## 一、原始需求复述

用户需要一款 macOS 原生文件复制管理工具，体验对标 TeraCopy：复制后可校验、保留时间戳、任务队列、失败重试、进度与速度可视化。当前 TeraCopy 在 macOS 上只有英文缩水版（1.1，无校验队列/脚本），Windows 4.x 独占，**市面上不存在令人满意的 macOS 中文版本**，这是立项理由。

### 关键背景事实（已核实）

| 事实 | 来源 |
|---|---|
| TeraCopy 4.x 仅支持 Windows 10/11 + Server 2016–2025 | 官方 |
| TeraCopy macOS 版停在 1.1（2024-12-18 更新以支持 Apple Silicon），纯英文、无中文、无任务队列、无脚本 | 官方 |
| macOS 版仅 4 种校验（MD5/SHA-1/SHA-256/SHA-512），远少于 Windows 版的 17 种/50+ 变体 | 官方 |
| 目标机：Apple M5（10 核 / 16GB）、macOS 27.2、可用磁盘仅 **30 GiB** | 实测 |

> **架构红线**：磁盘仅剩 30 GiB，禁止"先复制一份再校验一份"的落盘双份方案；校验必须**流式**进行（复制时 tee 哈希，或复制后原位回读比对），峰值额外磁盘占用 ≤ 单文件大小。

## 二、产品定义

### 2.1 一句话定位

**MacCopy 是一款纯原生、简体中文的 macOS 文件复制管理器：在后台以多线程高速搬运文件，复制的同时完成完整性校验，并提供可追溯的任务队列与失败重试。**

### 2.2 产品目标（可验证）

| # | 目标 | 验收指标 |
|---|---|---|
| G1 | **速度不输 Finder 原生** | 在同一 APFS 卷内复制 100 GB 混合文件（1 KB–2 GB，含 ≥10 万小文件），MacCopy 总耗时 ≤ `cp -R` 的 1.2 倍；单文件 ≥1 GB 顺序吞吐 ≥ 1.5 GB/s（NVMe 内置盘） |
| G2 | **复制完整性可证明** | 对人为篡改的样本文件（改 1 字节）执行复制后校验，100% 检出并标记"校验失败"；误报率 0（正确文件不报错） |
| G3 | **长任务不打断用户** | 复制 100 GB 期间，App 主窗口帧率 ≥ 55 fps、内存占用 ≤ 300 MB、CPU 占用 ≤ 单核 200%（10 核机）；App 可正常最小化/后台运行 |
| G4 | **零丢失、可恢复** | 强制中断（进程 kill / 电源断）后重启，任务能从断点继续，已完成文件不重复传输；任意时刻未完成文件均有 `.maccopy.partial` 残留且可被恢复 |
| G5 | **全中文、无学习成本** | 界面 100% 简体中文（含系统语言为英文的机器）；所有文案与错误码均有中文表述；零英文裸露字符串 |
| G6 | **跨介质健壮** | NAS（fnOS / iNAS）与 SMB 共享上的复制，在目标机在线、链路抖动场景下不产生损坏文件；不 seek 的流式源仍可完成校验 |

### 2.3 目标用户

| 画像 | 特征 | 核心诉求 |
|---|---|---|
| **A. 素材搬运者（主力）** | 中文用户，Mac 日常搬照片/视频/素材库，有 NAS（飞牛 fnOS、iNAS）、多台设备 | 大批量复制不能卡死界面；速度可量化；复制后校验能发现 NAS 静默损坏 |
| **B. 备份/迁移执行者** | 换机、升级硬盘、外接 SSD 迁移 | 断点续传、时间戳保留、失败可重试、报告可归档 |
| **C. 开发者/运维** | 需要脚本化、报告导出、CI 可用 | 任务队列、脚本钩子、日志、CLI（Pro 预留） |

### 5.6 Finder 集成方案对比与推荐

| 方案 | 能力 | 限制 | 结论 |
|---|---|---|---|
| **A. Finder 扩展（Sync Extension）** | 可在 Finder 右键/侧边栏做自定义 UI | **必须沙盒**；仅能作用于被授权的目录；无法覆盖系统服务菜单；审核复杂；扩展进程生命周期受限 | ❌ 不作为主方案 |
| **B. macOS Service（服务菜单）** | Finder「右键 → 服务」菜单；可传文件列表（NSItemProvider）；非沙盒下可访问任意路径 | 菜单层级较深；需用户手动启用（系统设置 → 键盘 → 服务） | ✅ **推荐为主方案** |
| **C. 独立 App + 文件监听（FSEvents）** | 监听目录变化自动触发复制；可做自动化 | 无用户交互触发；误触发风险；隐私权限（完全磁盘访问）提示 scary | ⭕ 作为 P2「自动化触发」补充 |

**推荐结论：以 B（Service）为主路径 + C（FSEvents）作 P2 预留。**
理由：Service 是 macOS 上唯一既能接收 Finder 多选文件列表、又能保留非沙盒全路径访问能力的官方机制；Finder Sync 扩展因强制沙盒反而无法满足"访问 NAS 挂载点/外接盘任意路径"这一核心诉求；FSEvents 单独使用缺少触发精度，故降级为 Pro 自动化能力。

## 六、关键技术约束与风险（供架构师参考）

| # | 约束/风险 | 说明 |
|---|---|---|
| K1 | **磁盘仅剩 30 GiB** | 禁止落盘双份校验；校验必须流式（tee / 原位回读）；禁止"先复制到临时区再改名"以外的额外占用 |
| K2 | **APFS 克隆 vs 跨卷** | `copyfile` + `COPYFILE_CLONE` 仅同卷生效；跨卷/跨文件系统必须走流式回退，需显式区分两条路径 |
| K3 | **长路径** | macOS 无 `\\?\` 前缀；PATH_MAX=1024 字节、单级名 255 字节。方案：逐级 `chdir` + 相对路径打开，或 `fcopyfile` 的分块 API；不可依赖单次 `open()` 长路径 |
| K4 | **不可寻址源** | SMB/网络流不可 seek → 复制后回读校验不可行 → 必须用 tee 单遍哈希；若 tee 也不可行则降级为"仅字节数比对"并明确标注 |
| K5 | **沙盒 vs 全权限** | 全盘访问、外接卷、SMB 挂载、Service 跨 App 传文件都需要非沙盒；走 Developer ID 直发路线 |
| K6 | **BLAKE3 无系统实现** | CryptoKit 无 BLAKE3；MD5/CryptoKit 亦无 → 需引入第三方 Swift 实现或 Rust/C FFI，需在包体积与许可证上评估 |
| K7 | **文件占用** | macOS 无强制独占锁，需用 `open` + `flock` 探测 / `fuser` 类启发式，避免误判导致频繁失败 |
| K8 | **Swift 6 严格并发** | 复制引擎须置于 `actor`；UI 状态经 `AsyncStream` 单向回传；所有 `@MainActor` 隔离边界需显式标注 |
| K9 | **时间戳精度** | APFS 支持纳秒级；HFS+/FAT/exFAT 精度不同，跨类型目标需声明精度降级 |
| K10 | **通知/Service 唤起开销** | Service 进程需冷启动时延 < 1.5 s 打开主窗口，需预热与共享进程优化 |

## 七、待确认问题（需主理人 / 用户拍板）

### Q1 分发模式：Developer ID 公证直发（非沙盒） vs Mac App Store（沙盒）
- **推荐：Developer ID 公证直发（非沙盒）**
- 理由：Finder Service 集成、外接盘 / NAS / SMB 任意路径访问、断点续传的文件系统级操作都需要沙盒外权限；App Store 沙盒会直接否决 P0-01/P0-11/P0-03（外接卷）与 Finder 集成。代价是需要开发者账号 + 每半年续签 + 用户需手动"允许来自 unidentified developer"，需在首启做引导。
- 备选：双轨（App Store 版砍掉 Service/外接卷），成本翻倍，不建议 v1。

### Q2 最低系统版本
- **推荐：macOS 13.0 Ventura**
- 理由：覆盖 2022 至今的活跃机型；SwiftUI `NavigationSplitView`、`Charts`/`Canvas`、`AsyncStream` 在 13 上均可用；`copyfile` 克隆语义、`FSSeek`/稀疏探测 API 自 10.13 起可用。若目标用户集中在新机可抬到 14/15，但会砍掉相当一部分用户。
- 需确认：目标用户是否包含 macOS 12 及以下的旧机器？

### Q3 校验算法依赖方案（尤其 BLAKE3 与 MD5）
- **推荐：引入成熟的第三方 Swift BLAKE3 实现（如 `blake3-swift` 绑定），MD5/CRC32 自行实现（代码量小、可控），SHA-1 用 CryptoKit（系统自带）**
- 理由：BLAKE3 是 TeraCopy 的招牌能力（速度快），但 CryptoKit 无此算法；第三方绑定会增加构建复杂度与包体积（约 +1 MB，可接受）。CRC32 与 MD5 自行实现可避免再引入依赖，且便于做硬件加速（CRC32 用 PCLMULQDQ）。
- 备选：v1 只做 CRC32 + SHA-1（零依赖），BLAKE3 延后到 v1.1。
- 需确认：是否接受引入第三方依赖？是否对许可（MIT/Apache）有硬性限制？

### Q4 长路径的技术实现路径
- **推荐：统一采用"逐级 chdir + 相对路径"的文件访问封装层（自研 `PathWalker`），并在必要时用 `openat()` 系列相对系统调用**
- 理由：这是 macOS 上唯一可靠绕开 PATH_MAX 的方式；`fcopyfile` 对超长路径支持有限度，需实测后决定是否走自研读写通道。
- 需确认：是否接受为长路径单独实现一套 I/O 通道（增加代码量与测试面）？还是接受"超长路径给出明确中文提示并降级"？

### Q5 不可寻址源（SMB / 网络流）的校验策略
- **推荐：默认走"复制时 tee 单遍哈希"，仅在源可 seek 且用户选了"仅失败时回读"时做回读；两者都不可用时降级为字节数+可读性校验，并在 UI 明确标注"未做内容哈希"**
- 理由：这是唯一在流式源上仍能给出内容级保证的方案；不应静默降级。
- 需确认：是否接受在"未做内容哈希"时于校验报告中显著警示（而不是默默通过）？

### Q6 断点续传的持久化介质与清理策略
- **推荐：断点元数据存 `~/Library/Application Support/MacCopy/Resume/`，分片文件与目标同目录（`<name>.maccopy.partial`）；提供"清理已完成/陈旧分片"入口并保留最近 7 天**
- 理由：分片必须与目标同卷才能续写；元数据放 App Support 可在 App 重启后恢复。
- 备选：分片统一放临时目录 → 但跨卷续写性能差、且临时目录易被系统清理。
- 需确认：分片文件用 `.` 前缀隐藏，是否可接受用户看不到中间态（Finder 默认隐藏点文件）？

### Q7 校验失败后的默认动作
- **推荐：默认"标记失败 + 自动重传 1 次"（仍失败则进失败列表）**
- 理由：多数校验失败源于传输抖动而非真实损坏，自动重传一次能显著降低误报；真实损坏在重传后仍会被检出。
- 需确认：是否需要用户逐项确认，还是允许默认自动重传？

### Q8 Pro 版授权与商业模式
- **推荐：v1.0 不接任何授权 SDK，仅用编译期 Feature Flag（`FeatureFlags.proFeaturesEnabled`）+ 设置页"Pro 功能（规划中）"区块；v2.0 再评估 Paddle / LicenseKit**
- 理由：避免在功能未完整前引入支付与凭证校验链路；架构上所有 Pro 点只通过协议 + 开关访问，切换成本低。
- 需确认：Pro 定价区间与是否需要中文支付渠道？

### Q9 "免费版 2 线程" 是否作为硬上限
- **推荐：是**，与 TeraCopy 免费版对齐；设置中允许用户调到 8 线程但超过 2 线程时提示"Pro 专属（规划中）"，v1 实际强制 2**
- 理由：免费版与 Pro 划分的"可感知差异点"就是并发度与自动化能力。
- 需确认：是否宁可先放开到 4 线程换口碑？（会削弱 Pro 购买动机）

### Q10 Finder 集成的用户可达性
- **推荐：Service 为主，并在 App 首次启动做 3 步图文引导（系统设置 → 键盘 → 快捷键 → 服务 → 启用「用 MacCopy 复制」），同时提供"复制到…"的右键上下文菜单（Service 做不到上下文菜单）**
- 理由：Service 在系统设置的二级层级里，默认不可达；没有引导会导致集成功能无人使用。
- 需确认：是否接受在 App 内嵌"打开系统设置"深链（`x-apple.systempreferences:com.apple.Keyboard-Services.extension`）？

### Q11 稀疏文件在 SMB 目标的处理
- **推荐：自动模式 —— 目标支持稀疏（本地 APFS/HFS+）则保留；不支持（exFAT/FAT32/SMB）则常规写入并在报告标注"未保留稀疏（目标文件系统不支持）"**
- 理由：SMB 上普遍无法创建空洞，强行使用 `ftruncate`+seek 会产生真实稀疏但服务端可能不支持，风险高。
- 需确认：是否需要提供"强制尝试稀疏写入"的实验开关？

### Q12 界面语言锁定策略
- **推荐：v1.0 强制简体中文（无论系统语言），但所有文案进 String Catalog，v1.1 加英文**
- 理由：立项理由就是"没有中文版本"，第一版把中文化做到极致比双语更契合目标用户。
- 需确认：是否有英文用户诉求？

## 附录 A：文件枚举参数语义澄清（QA-2 的 Q2）

> 本附录为**已有行为的文档化澄清**，不改变任何需求、验收标准或代码。`FileEnumerator.Options` 在 T04 实现时未在 PRD/架构中定义语义，QA-2 提出「`maxDepth` 易被下游误用」，故补此说明。

### A.1 `maxDepth` 定义

| 项 | 说明 |
|---|---|
| 类型 / 默认值 | `Int`，默认 **`0`** |
| 语义 | **最大递归深度**；`0` = **不限** |
| depth 起算 | 源根目录的**直接子项为 depth 0**；每进入一层子目录 `depth + 1`（`FileEnumerator.swift:61` 以 `depth: 0` 起，`walk` 递归时传 `depth + 1`） |
| 判定位置 | `walk` 入口 `if options.maxDepth > 0, depth > options.maxDepth { return }`（`FileEnumerator.swift:100`）——**先判定再枚举当前层的子项** |
| 取值范围效果 | `maxDepth = N > 0` 时枚举 **depth 0 … N** 的条目；`depth = N+1` 及更深**不展开**。例：`maxDepth = 1` 产出 depth0 直接子项 + depth1 子项，不展开 depth2 |
| 边界 | `0` 表示不限（**不是**「只枚举根目录」）；负数因 `maxDepth > 0` 为 false 也等同不限，但**调用方不得传负数** |
| 与 P0-11 的关系 | `maxDepth` 是**逻辑层级限制**，与 macOS `PATH_MAX` / 40 级嵌套支持无关。**P0-11 长路径验收必须使用默认 `maxDepth = 0`（不限）**；默认值本身也不影响 P0-11 |

### A.2 `FileEnumerator.Options` 全量参数（便于下游查阅）

| 参数 | 默认值 | 语义 |
|---|---|---|
| `includeHidden` | `true` | 是否包含隐藏文件 |
| `followSymbolicLinks` | `false` | 是否跟随符号链接指向的目录（默认 false 以防循环） |
| `probeSparse` | `true` | 是否探测稀疏信息（对应 P0-12 稀疏文件处理） |
| `maxDepth` | `0` | 最大递归深度，`0` = 不限（见 A.1） |

**给验收的提示**：涉及「10 万小文件」「40 级嵌套」等 P0-11/性能专项时，须显式确认 `maxDepth == 0`，否则样本会被截断导致假通过或假失败。

## 附录 B：性能类验收的测量口径（产品裁决）

> 本附录为**验收方法论的产品裁决**，不改变任何性能目标数值。起因：QA 在 CI 满载期间观察到 `ThroughputTests.swift` 的 BLAKE3 门槛连续误报（0.561–0.983 GB/s），独立探针同时段同样降到 0.610–0.874 GB/s，而 BLAKE3 官方向量 35/35 仍全过——根因是并发 `build.sh` 抢 CPU 的时序抖动，非算法回归。

### B.1 裁决结论

| 决策点 | 结论 |
|---|---|
| **Q3 硬指标 `BLAKE3 ≥ 1.0 GB/s`（单线程）是否放宽？** | ❌ **不放宽**。这是产品招牌指标（对标 TeraCopy 的 17 种算法/50+ 变体能力），属产品目标范畴，**不得由测试侧自行下调**（QA 建议的「降至 0.8 GB/s」不采纳；若确需调整须主理人/用户重新拍板） |
| 是否允许 `skip` / `xfail` /  swallow 失败 | ❌ 不允许。门槛仍是硬断言，无豁免 |
| **可以改的是什么** | ✅ **测量口径**（时序型指标的采样方式），不是目标值 |
| **「多次取最优」是否有次数上限** | ✅ **固定 8 次**（与当前 `ThroughputTests.swift` 实现一致：高优先级专用线程 + 8 次取最优），**不得追加次数**；且**必须记录全部 8 次采样值**。若 8 次串行 / Release / 无并发 `build.sh` 的采样**全部**低于 1.0 GB/s，则**不再重跑**，直接判定为真实性能回归并回报，进入 Q-A14 的 ≥64 MiB 分段并行预案评估。**禁止用「再跑几次总能过」掩盖实际退化**，否则硬门槛形同虚设（主理人最终口径：8 次；10 次连续运行零失败） |
| 算法正确性与吞吐的关系 | **解耦**：算法正确性以官方 test vectors（35/35）为唯一判据；吞吐不达标 ≠ 算法错误，不得据此回滚实现 |

### B.2 性能类验收的统一测量口径（G1 / Q3 / 全部吞吐基准适用）

1. **串行执行**：测量期间不得并发 `build.sh` / 其他 CPU 密集任务；CI 中性能用例须排在构建之后单独运行。
2. **Release 构建**：Debug 构建慢 10× 以上，测量值无效。
3. **固定 8 次独立测量取最优**：禁止单次采样直接判定；**次数上限固定为 8 次，不得追加**；**必须记录全部 8 次采样值**而非只记最优值。当前实现为「高优先级专用线程 + 8 次取最优」，示例输出：`BLAKE3 吞吐：1.096 GB/s（256 MiB / 0.245 s，8 次取最优·高优先级线程）` + `全部采样(GB/s)：[1.096, 1.072, 1.052, 1.057, 1.018, 0.956, 0.987, 0.960]`。
4. **单次低于门槛不得直接判回归**：以本轮 8 次采样的**最优值**判定；若 8 次中有任一次 ≥ 1.0 GB/s 即通过。测量前须确认「串行 / Release / 无并发 `build.sh`」三项前提；若前提不满足，先修正环境后**重新执行一整轮 8 次采样**（这属于前提修正，不算追加次数、不算重跑作弊）。
   **⚠️ 重跑的前提违反必须可指认且留痕（v1.9 补，v1.11 收紧为「可观测事件」）**：验收报告须写明**具体是哪一项前提被违反**及修正动作，且**「可指认」仅指可观测事件，不接受推测或结论性措辞**：

   | 类别 | 具体项 |
   |---|---|
   | ✅ **可指认（可观测事件）** | ① 同一时间窗内存在另一个 `build.sh` / `swiftc` 进程（**PID 或日志时间戳与采样窗口重叠**）；② 编译输出出现 `modified during the build`；③ 构建模式不是 Release（`-O` 缺失）；④ 采样序列出现**明确双峰 / 长尾**（非整体平移） |
   | ❌ **不可指认（推测，禁止作为重跑理由）** | 「负载高」「感觉在抢 CPU」「排除环境争用后重跑」等结论性措辞；`getloadavg()` 数值本身**不足以**指认前提违反（单看数值方向可能与争用相反） |

   **形式化示例（不引用任何真实执行）**：
   - **合规**：报告写明「测量期间检测到并发 `build.sh` 进程（PID ××，时间戳与采样窗口重叠）」，修正为串行后重新执行一整轮 8 次采样并留痕。
   - **违规**：仅以「负载略高」「再跑一次说不定就过」为由重跑，且无法指认具体前提违反 → **直接适用第 5 条终局判定，不得重跑**。

   **禁止事后补前提**：不得为了留痕而在事后替某次重跑补写一个前提；若当时记录不支持「可指认」，该次重跑即按违规处理。**本条不回溯判定历史执行**，也不以任何单次重跑作为合规范例。
5. **8 次全部低于门槛即终局判定**：在三项前提均满足的前提下，8 次采样**全部** < 1.0 GB/s → **不再重跑**，直接判定为**真实性能回归**并回报，进入架构 Q-A14 的降级预案（≥64 MiB 文件启用分段并行）评估，同步主理人评估是否调整产品目标。**严禁「再跑几次总能过」**——这会让硬门槛形同虚设。
6. **记录要求**：验收报告须同时列出「全部 8 次采样值 / 最优值 / 构建模式（Release / `-O`） / 当时负载（`getloadavg()`） / 是否满足三项前提」，便于复现与审计。

**给 G1 的连带提示**：G1 的「100 GB 混合文件耗时 ≤ `cp -R` 的 1.2 倍」「单文件 ≥1 GB 顺序吞吐 ≥1.5 GB/s」同属时序型指标，同样适用 B.2 口径；但 **1.2 倍 / 1.5 GB/s 两个数值同样不放宽**。

### B.3 测量实现的加固记录（属测量口径，不改变任何验收标准）

> 以下三项是工程师在落实 B.2 时踩到并绕开的实现层问题，记录于此以便复现与后续维护。**均为测试代码加固，不改动产品代码、不改动任何性能目标或验收断言**。

| # | 问题 | 加固做法 |
|---|---|---|
| B.3-1 | Swift 6 严格并发下 **async 上下文禁用** `semaphore.wait()` / `Thread.sleep()` | 将 `measureBLAKE3` 拆为**同步非 async 函数**，基准逻辑在同步上下文执行，避免与 async 运行时约束冲突 |
| B.3-2 | `UnsafeMutableRawPointer` **非 Sendable**，跨并发边界传递会被 Swift 6 拦截 | 用 **`UInt(bitPattern:)` 传标量**（把指针转成整数标量传递），规避对非 Sendable 类型的限制 |
| B.3-3 | 并发运行译文完整性测试时，多个用例**同时篡改** `translations/*.json` 互相踩踏，产生假失败 | 增加 **`ensureHealthyTranslations()` 前置检查**，任一用例发现译文文件被污染即**以 `.atomic` 立即恢复**；保证每次测量/校验起点一致 |

**约束**：B.3 三项不得被解读为放宽 B.1 / B.2 的任何一条；尤其 `ensureHealthyTranslations()` 只「从冻结快照 + TSV 重建损坏的译文文件」，**不得绕过 `--check-languages` 的五项硬校验**（零缺失含多余 key / 占位符数量与类型 / 空串全空白 / `zh-Hant` 简体字扫描 / **基准占位符签名未漂移**）及并列的中文基准快照 180 条逐字比对；重建后仍须逐条全跑（与 `docs/PRD-I18N.md` §2 / P0-17 ④ 口径一致）。

> **口径修订记录**：附录 B 初稿按「固定 5 次」写入；主理人最终裁决与工程师实际实现均为 **8 次**（高优先级专用线程 + 记录全部采样值 + 取最优，10 次连续运行零失败），现全文统一为 **8 次**。B.1 / B.2 的其余裁决（Q3 1.0 GB/s 不放宽、无 skip/xfail、串行 / Release / 无并发 `build.sh`、全部低于即终局判定、正确性以 35/35 官方向量为唯一判据）**一律不变**。
